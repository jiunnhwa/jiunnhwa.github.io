13 S-Curve Limit & Receptivity

Jiunn's caution: more oracles may not mean better results. There is an S-curve limit where additions introduce noise, not accuracy.

Receptivity Test (4 gates)

  1. Produces elements? — Can it feed the bridge table?
  2. Semantic equivalence? — Does "Fire" mean the same across systems?
  3. Independent signal? — Genuinely different from existing oracles?
  4. Passes 3Ps? — Philosophy, Physics, Programmable?
Principle
A three-oracle engine with clean signal beats a ten-oracle engine with noise. Engine power comes from selectivity, not completeness.

16 Retrospective

What Went Well

  • Theory was productive, not decorative. MapReduce, bridge table, cardinality analysis — all produced validated architecture and working code.
  • Lotus POC comparison cycle effective. Three rounds, each isolating one issue. Bridge table concept emerged from debugging.
  • Lucky Profile shipped. From concept to working HTML in one session. Join table with two sources is genuinely new.
  • S-curve / receptivity discussion. Prevented premature oracle additions. Established design constraint.
  • Zero technical debt. Not luck — the front-loading of theoretical work keeps the implementation clean.

What Could Be Better

  • CSV index bug. parts[4] vs parts[3] — took two debug runs. Should have caught immediately.
  • Indentation drift. compute_lucky at module level. Basic Python structural error.
  • Missing HTML renderer. Generated MD and compute but forgot render.py entirely.
  • Constants not updated. _SECTION_NAMES, _SECTION_ORDER, _SECTION_TYPE_MAP should have been updated with initial code generation.

Improvement: Checklist Discipline

When adding a new section/feature, enumerate all touchpoints before writing code:

  1. tree.py: compute function + constants + section registration
  2. render.py: render function + dispatch registration
  3. render_md.py: block function + blocks dict
  4. index.tpl: section container + sidebar + CSS
  5. report.tpl.md: placeholder
